# Legacy implementation audit

The original `js/main.js` established the project’s low-poly look, but loading, placement, camera wrapping, traffic, collision checks, and rendering shared one global frame loop. The redesign keeps the visual assets and replaces those coupled behaviors with explicit, tested invariants.

| Legacy behavior | Failure mode | Replacement | Invariant |
| --- | --- | --- | --- |
| Z-boundary checks changed `car.position.x` | Northbound and southbound vehicles crossing a Z limit were moved sideways by 480 units every frame and disappeared. | `src/traffic/lanes.ts`, `src/traffic/spawning.ts`, and `src/traffic/simulation.ts` | A vehicle advances only through scalar lane progress; direction maps that progress to exactly one world axis, and recycling never applies a wrong-axis correction. |
| Collision rays started at `car.position.x + 58` | Car transforms were local to the loaded `cars.gltf` scene, while the hard-coded correction approximated a parent offset in world space. Collision behavior depended on an accidental coordinate-space relationship. | `src/traffic/lanes.ts` and `src/rendering/traffic-view.ts` | Simulation positions are logical world coordinates. Rendering alone subtracts the render origin; no parent-scene correction enters traffic rules. |
| Every car raycast against every car hierarchy | The quadratic all-car query had no lane model, no explicit leading-car selection, and could intersect the querying model’s own hierarchy. | `src/traffic/following.ts` | Active vehicles are grouped by lane, ordered by scalar progress, and constrained only by their nearest logical leader or stop line. No traffic raycasts are used. |
| Speed and acceleration were per-frame constants | Vehicle behavior changed with refresh rate and slowed or accelerated differently under load. | `src/traffic/following.ts`, coordinated by `src/app.ts` | Traffic advances in fixed 1/60-second steps with a capped accumulator; rendering interpolates without changing simulation results. |
| Direction offsets followed `if (direction)` | All defined non-zero directions entered the first branch, so the later east/west/north offsets were unreachable. The dormant north branch also referenced an undefined variable. | `src/city/layout.ts`, `src/rendering/city-view.ts`, and `src/traffic/lanes.ts` | Quarter turns are explicit values with an exhaustive transform table; traffic directions are an exhaustive four-value type with authored lane offsets. |
| A fixed 8×8 board was disguised by camera and car teleports | Separate magic bounds and leap distances made the world repeat, coupled camera motion to vehicle transforms, and exposed discontinuities. | `src/city/tile-window.ts`, `src/city/origin.ts`, `src/camera/controller.ts`, and `src/rendering/city-view.ts` | Logical camera coordinates are unbounded. A fixed tile pool streams deterministic coordinates, while render-origin shifts occur only in whole 60-unit blocks and never mutate simulation state. |
| Repeated placements loaded and parsed the same building files repeatedly | Duplicate instances paid repeated network/parse cost and made resource ownership unclear. | `src/rendering/assets.ts` | Each of the 17 asset URLs is requested once. Cached prototypes are cloned for pooled views, with shared visual resources retained for the application lifetime. |
| Traffic was omitted when `screen.width <= 768` | Mobile users saw an empty city instead of an adapted simulation. | `src/rendering/quality.ts` and `src/app.ts` | The mobile profile creates exactly 20 vehicle slots and keeps all four directions; quality is selected from CSS viewport width once per session. |
| Obsolete `gammaInput`, `gammaOutput`, and `gammaFactor` flags configured color | Removed Three.js APIs made output dependent on an old renderer version. | `src/rendering/scene.ts` | The renderer uses `THREE.SRGBColorSpace`; pixel ratio and shadow resolution come from an explicit quality profile. |
| Loading had only progress and success callbacks | A required failure could leave the loading presentation indefinitely, and WebGL/context failures had no recovery path. | `src/rendering/assets.ts`, `src/app.ts`, and `src/ui/overlay.ts` | Optional buildings fall back to the park or an empty plot; missing/invalid vehicle prototypes construct no simulation or traffic view; required road/WebGL/frame failures show a readable retry state; context loss pauses until restoration. |

These replacements deliberately separate logical state from Three.js objects. The pure city and traffic modules can be verified without a DOM, renderer, or loaded model hierarchy.

Traffic recycling also observes the visual boundary explicitly: production keeps active vehicles through the 300-unit fog-far distance, removes them only beyond the 420-unit simulation radius, and accepts replacements only beyond fog.
